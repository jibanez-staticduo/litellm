# Post Implementation Task Updates

## Technical Architect: Investigation Result

### Summary

The candidate has no ASGI registration, route-order, component-allowlist, root-path, or lazy-loading defect. The exact retained image contains all six concrete discovery routes and all three LazyMCP transports. Starlette reports a `FULL` match for the aggregate inserted route, and the equivalent direct-router probe returns HTTP 200 for all six aliases when `PROXY_BASE_URL=https://gateway.example` is set

The observed 404s are application-generated by the discovery handler's trusted-public-base fail-closed branch. TASK-006 ran the isolated container with no `PROXY_BASE_URL`; Docker bridge requests arrived over HTTP from a non-loopback peer. `_trusted_base()` therefore rejected the request even when its Host was loopback-like, `parse_lazymcp_resource()` returned `LazyMcpResourceError`, and `_lazymcp_protected_resource_metadata()` deliberately raised `HTTPException(404, "Not Found")`. OpenAPI reports registered routes without executing this runtime trust policy, which explains the apparent OpenAPI/live divergence

The same rejected trusted-base calculation explains the challenge results. Every direct transport preserves `_original_path`, but `_lazymcp_challenge()` calls `resource_from_transport_scope()`, receives `LazyMcpResourceError`, and returns `None`. Authentication then follows the pre-existing fallback: aggregate `/lazymcp` reaches `_gateway_dcr_challenge()` and advertises legacy `/mcp` metadata, while scoped and toolset requests continue into their existing catalog/database paths and produce the observed generic 401, 400, or 503. With the same retained image and a valid configured HTTPS public base, direct challenge-builder probes return the exact aggregate, scoped, and toolset LazyMCP metadata URLs

### Minimal Correction

Do not weaken `_trusted_base()` and do not change application runtime source for this finding. The smallest correct fix is to correct the isolated TASK-006 smoke contract: start the candidate with a non-secret `PROXY_BASE_URL=https://candidate.invalid` (or another reserved HTTPS test authority), send requests with the matching authority, and assert all returned `resource`, `authorization_servers`, and absolute `resource_metadata` values against that configured base. This models TLS termination and gives the security-sensitive URL builder an explicit trusted external identity without trusting Docker bridge peers, request-controlled Host, or forwarded headers

Add two mutation-sensitive regressions to the existing mapped files before rebuilding:

1. In `tests/test_litellm/proxy/_experimental/mcp_server/test_lazymcp_public_resource.py`, extend the real-app/direct-router discovery matrix with a Docker-like non-loopback peer over HTTP and no `PROXY_BASE_URL`; assert generic 404 for all six aliases. Then set an HTTPS `PROXY_BASE_URL` and assert all six return 200 and exact metadata. This pins the diagnosed fail-closed/configured-success boundary
2. In `tests/test_litellm/proxy/_experimental/mcp_server/auth/test_user_api_key_auth_mcp.py`, extend the existing three-resource challenge matrix with the same Docker-like untrusted scope. Assert `_lazymcp_challenge()` does not fabricate a Host-derived challenge when no trusted base exists, then assert exact aggregate/scoped/toolset challenges when the HTTPS configured base exists. Keep no-token versus invalid-token and selection-header invariance assertions

The candidate smoke harness/logging should also record only whether the public-base variable is present and the expected public authority, never environment dumps or credentials. It must validate route matches plus HTTP outcomes separately so a future handler-generated 404 is not mislabeled as an unregistered route
